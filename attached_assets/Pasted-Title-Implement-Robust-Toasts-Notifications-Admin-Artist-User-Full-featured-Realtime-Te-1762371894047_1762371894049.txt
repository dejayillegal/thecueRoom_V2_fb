Title: Implement Robust Toasts & Notifications (Admin / Artist / User) — Full-featured, Realtime, Testable in Replit

Summary
-------
Deliver a complete, production-quality Toast + Notifications system usable by Admins, Artists and Users. Features must include:

- Global Toast Provider with `useToast()` API (create/update/dismiss, pending→update, action buttons, undo).
- Notifications backend & UI (in-app panel + unread badge), realtime delivery, mark-read/unread, deep links.
- Notification preferences per user (email digest, in-app types, do-not-disturb window).
- Admin tools to send system broadcasts, targeted notifications and view notification audit logs.
- Batching & rate-limiting to avoid spam.
- Safe Replit demo mode (no external push required; mock email & push).
- Full tests, Storybook stories, migrations, docs and runbook.

High-level requirements & behaviors
----------------------------------
1) Toast Provider & UX
   - `useToast()` returns `{ toast(opts) -> id, updateToast(id, opts), dismissToast(id) }`.
   - Toast types: success, error, info, pending.
   - Support pending toasts that are updatable (e.g., "Verifying…", then updated to "Verified!").
   - Toasts can include action buttons (e.g., Undo), custom durations, and priority.
   - Toast stacking with visible max (e.g., 5) and queueing.
   - Accessible: `role="status"` / `aria-live` usage; keyboard focusable actions.
   - Storybook stories for each toast variant and pending→update flow.

2) Notifications Backend & Delivery
   - `POST /api/notifications/send` (admin/system):
     - Body: `{ target: { userIds?:[], role?:'admin'|'artist'|'user', all?:boolean }, type:'system'|'verification'|'comment'|'follow'|'promo', title, body, payload }`
     - Validated by Zod and permission-guarded for admins.
     - Creates DB records and enqueues delivery job.
   - `GET /api/notifications/list?cursor=&limit=&filter=` returns paginated notifications for authenticated user (Zod validated).
   - `POST /api/notifications/mark-read` accepts `ids[]` or `all=true`.
   - Realtime: use Supabase Realtime or WebSocket to push new notifications to connected clients. If not available, provide a fallback SSE or poll endpoint.
   - Delivery adapters:
     - In-app push: write to DB and broadcast via realtime channel.
     - Push notifications (optional): adapter interface; in Replit demo it uses mockPushAdapter to log and create audit entries.
     - Email digest: worker aggregates and sends digest using mock/email adapter in demo.

3) Notification preferences & DND
   - Users can set preferences in UI: enable/disable in-app, push, email digest; mute types; set DND window (start/end).
   - Preferences respected by delivery worker: do not push during DND; queue for digest.

4) Batching, rate-limits & de-duplication
   - Worker batches multiple similar notifications (e.g., many likes) into a single summary notification within a short window.
   - Rate-limit per user configured by `NOTIFICATION_RATE_LIMIT`.
   - De-duplication: identical payloads within a time window are merged.

5) Admin features
   - NotificationComposer (admin UI) to craft targeted messages, schedule broadcasts, and preview.
   - Audit log for all send actions, visible in NotificationAuditLog component.
   - Admin may force-send or cancel scheduled notifications.

6) Toast analytics
   - Optional endpoint `/api/toasts/track` to record user interactions with toasts (used for telemetry).
   - Respect privacy: no PII in telemetry.

7) Realtime & fallback modes
   - Primary realtime via Supabase Realtime (if project uses Supabase), else WebSocket fallback.
   - Provide an SSE/poll fallback for environments without realtime.
   - Replit demo mode: realtimeAdapter uses an in-memory pubsub and mockPushAdapter; logged to console.

8) Security & permission checks
   - Admin routes require admin role or DEMO_ADMIN_KEY in Replit.
   - All API payloads validated with Zod; return structured errors.
   - Ensure DB RLS policies (if using Supabase) enforce users only see their notifications.

9) Persistence & cleanup
   - Notifications older than 90 days archived; scheduled background job (worker) to cleanup (configurable).
   - Optionally, persistent toasts stored in DB for cross-device consistency.

10) Internationalization & templating
   - Notification templates support i18n keys and must accept `locale` and templated payload data.
   - Admin composer allows preview in different locales.

Developer notes & common pitfalls
--------------------------------
- Respect RLS policies if using Supabase: users should not be able to read others’ notifications.
- Keep the in-memory pubsub only for demo/testing; do not use in production.
- Rate-limiting must be enforced server-side to avoid notification storms.
- For production push notifications, integration with a push provider (Firebase / OneSignal) requires careful opt-in & privacy handling. Keep FEATURE_PUSH behind a flag.
- When batching, ensure important notifications (security, account changes) bypass batching and are immediate.
- Ensure worker idempotency for retries (e.g., use job IDs).
- Avoid sending toast telemetry that contains PII.
