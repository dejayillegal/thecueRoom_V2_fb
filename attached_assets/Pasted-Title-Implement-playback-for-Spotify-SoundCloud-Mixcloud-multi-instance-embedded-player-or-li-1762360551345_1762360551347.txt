Title: Implement playback for Spotify / SoundCloud / Mixcloud — multi-instance embedded player or light-weight embed + external-open fallback (choose priority)

Summary
-------
Goal: allow users to play weekly-curated playlists and tracks from Spotify, SoundCloud, and Mixcloud in thecueRoom in a way that works reliably for many concurrent users and devices. Provide two options; implement the chosen approach:

A) Full Embedded Playback (advanced) — in-app players with coordinated multi-instance logic so multiple users / tabs can play without conflicts. Requires more infra, user auth for some providers (Spotify Web Playback SDK needs Spotify Premium + user OAuth), and server tokens for metadata. Higher developer and running cost.

B) Embed + External-Open Fallback (recommended default if you want lower cost & simpler infra) — show embed widgets in dashboard for quick preview; when user clicks Play, open the playlist in the native web player or Spotify app (via deep link). This avoids in-app playback complexity and authentication costs and scales cheaply.

This task prompt implements both paths but prioritizes B as a low-cost default and A as an optional opt-in feature behind a feature flag.

High level design & decision rules
---------------------------------
1) Default / Recommended (Option B — Lightweight)
   - Use provider iframe/embed widgets for inline preview (Spotify embed iframe, SoundCloud widget iframe, Mixcloud iframe).
   - Show standard playback inside iframe, but do NOT attempt to control cross-tab or cross-user playback centrally.
   - Provide a prominent "Open in app" / "Open in web player" CTA:
     - Spotify: open web player via `https://open.spotify.com/playlist/{id}` or deep link `spotify:playlist:{id}` (mobile will open Spotify app where supported).
     - SoundCloud: open track/playlist link.
     - Mixcloud: open link.
   - Benefits: no user OAuth required, minimal infra, scales to many users, no premium needed.
   - UX: embed is for preview; clicking play can either play inside embed (user-local) or open external player for full experience — make this configurable.

2) Advanced In-app Playback (Option A — Opt-in)
   - For Spotify: integrate Spotify Web Playback SDK to control playback inside the app. **Important caveats**:
     - Requires **user authentication with Spotify** and the `user-read-playback-state` + `user-modify-playback-state` scopes.
     - Spotify Web Playback SDK requires the user to have a Spotify client (Premium) to play full tracks. For public previews you may still use preview_url, but that's limited.
     - This approach requires implementing OAuth flow, storing refresh tokens per user, and ensuring token refresh logic in backend.
   - For SoundCloud: the iFrame widget provides API for play/pause via `postMessage`; you can implement richer integration but the user playback is still within SoundCloud's widget.
   - For Mixcloud: embed widgets support playback but have limited programmatic control.
   - Multi-instance coordination:
     - Local tab coordination: use BroadcastChannel or shared ServiceWorker to ensure only one player plays in the same browser (auto-pause others).
     - Cross-device coordination (different users): not required — each user controls their playback. But if you want to provide a "DJ / shared session" feature, that needs additional design (websocket sync + leader session).
   - Cost & complexity: adds OAuth complexity, potential user friction, and higher development and operational cost.

3) Practical hybrid approach
   - Implement Option B (embed + external-open) first for fast rollout.
   - Provide an opt-in "Enable in-app playback (Advanced)" admin toggle (FEATURE_WEB_PLAYBACK) which, when enabled+configured, will:
     - Display "Play in-app" button that triggers Web Playback integration for Spotify for *logged-in users who connected their Spotify account* (progressive consent).
     - For users who haven't connected, gracefully fall back to embed/external-open flow.

Concrete implementation tasks (step-by-step)
--------------------------------------------
PHASE 1 — Embed + External-Open (Priority - Low cost, fast)
1. UnifiedEmbedPlayer component:
   - Accept props: `{ platform: 'spotify'|'soundcloud'|'mixcloud', url, embedUrl?, playlistId?, onOpenExternal? }`
   - If FEATURE_EMBED_FALLBACK true, render provider iframe embed (responsive, lazy load).
   - Show a clear "Open in Spotify App" / "Open in Web Player" button overlay on mobile & small screens.
   - Provide small metadata (title, artist, track count) by calling server metadata endpoints when needed (to display fallback native track list).
2. Server-side metadata endpoints:
   - Implement apps/web/app/api/player/spotify/metadata/route.ts which uses client credentials to fetch playlist metadata (title, description, cover image) from Spotify Web API to show native list fallback and to validate embed.
   - Similar for SoundCloud/Mixcloud if needed (optional).
3. Dashboard integration:
   - Update LatestPlaylistWidget to use UnifiedEmbedPlayer for the live playlist item.
   - Users clicking the embed's "Open in app" CTA should open the external link (deep link on mobile or web player link).
4. Tests & stories:
   - Storybook stories for UnifiedEmbedPlayer in each provider mode, showing embed & external-open button.
   - E2E test: Dashboard shows playlist, clicking external-open opens correct URL (assert URL formed correctly).

PHASE 2 — Progressive In-App Web Playback (Optional, behind flag)
1. Add admin config & feature flag FEATURE_WEB_PLAYBACK.
2. Spotify Web Playback implementation (only if admin enables and app has configured Spotify OAuth):
   - Implement OAuth connect flow for users: "Connect Spotify" button in profile. On success store refresh token/server-side token in secure table.
   - For connected users, allow Web Playback SDK usage:
     - Load SDK, initialize player with user token, and create a player instance.
     - Use SDK controls to play a playlist (requires user Premium). Show informative message if not Premium.
   - Implement GlobalPlaybackManager:
     - Use BroadcastChannel to notify other tabs in same browser to pause their players when a play event starts (local single-player behavior).
     - For each player instance, listen for play/pause events; when the user starts playback in one tab, send a "pause" message to other tabs to stop playback.
   - Implement graceful fallbacks:
     - If Web Playback fails (token expired, not Premium), fall back to embed/external-open with an informative toast explaining the limitation.
3. SoundCloud / Mixcloud programmatic control:
   - Use widget API (postMessage) to issue play/pause commands and to listen for events.
   - For cross-tab coordination, use same BroadcastChannel logic.
4. Analytics & telemetry:
   - Capture playback events: play, pause, track_changed, source (embed/webplayback), device (mobile/desktop).
   - Respect privacy - do not log user audio data; only events.
5. Tests:
   - Unit tests for GlobalPlaybackManager message handling.
   - Integration test for Spotify Web Playback flow with mocked tokens and mocked SDK (CI should mock SDK).

Security, privacy & UX rules
---------------------------
- Do not attempt to stream copyrighted content server-side to bypass provider rules.
- Respect provider TOS: use official embeds and SDKs.
- If using Spotify Web Playback SDK, require user consent (explicit "Connect Spotify" flow) and request only needed scopes.
- Always provide informative fallback messages: "Spotify Web Playback requires Premium — opening in Spotify App instead."
- Provide per-user settings: "Open playback by default in app" vs "Play inline preview".

API contracts (examples)
------------------------
- GET /api/player/spotify/metadata?playlistId={id}
  - returns { title, description, cover_image, track_count, tracks: [{id, title, artist, preview_url?}] }
- POST /api/player/validate
  - body: { url }
  - returns: { ok: true, platform, playlistId, embedUrl } or { ok:false, error }
- POST /api/player/spotify/connect (if Web Playback)
  - initiates OAuth redirect (server returns redirect url)
- GET /api/player/spotify/callback
  - handles OAuth callback; stores refresh token for user

Developer notes & pitfalls
--------------------------
- Spotify Web Playback SDK requires HTTPS (localhost with special flags in dev works) and Premium. Test accounts should be prepared.
- Many browsers restrict autoplay — user gesture required to start playback. Design UX accordingly.
- For SoundCloud and Mixcloud, embed widgets are the most robust approach; programmatic control exists but is limited.
- Avoid server-side streaming — use providers' SDKs/embeds only.
- Respect rate limits for metadata (cache server-side results for short TTL).
- On mobile, deep linking behavior varies by OS and installed apps; verify common mobile paths.
