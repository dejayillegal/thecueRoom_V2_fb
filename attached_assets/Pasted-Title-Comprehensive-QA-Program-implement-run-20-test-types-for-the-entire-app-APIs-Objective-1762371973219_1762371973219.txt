Title: Comprehensive QA Program — implement & run 20 test types for the entire app + APIs

Objective
---------
Implement, run and report a full testing program that validates the entire application (frontend, backend, workers, DB, integrations) and public/private APIs across the following test types:

1. Functional Testing
2. Integration Testing
3. Load Testing
4. Stress Testing
5. Security Testing
6. Reliability Testing
7. Usability Testing
8. Documentation Testing
9. Regression Testing
10. Fuzz Testing
11. Compliance Testing
12. Performance Testing
13. Scalability Testing
14. Compatibility Testing
15. Error Handling Testing
16. Unit Testing
17. Contract Testing
18. Negative Testing
19. End-to-End Testing
20. Penetration Testing

This prompt tasks you to implement automated test suites where possible, define manual procedures where needed, integrate tests into CI, produce pass/fail reports and remediation tasks.

Scope
-----
- Frontend (Next.js web app components, Storybook)
- Backend (Next App Router API routes, workers, scheduler)
- DB (Postgres via Supabase/Drizzle)
- Integrations: OpenAI, Spotify, Supabase, storage, email
- Mobile/web responsive checks where applicable
- Environment: local dev, staging, CI (GitHub Actions / Replit CI)

Deliverables
------------
1. Test suites and scripts organized in repo (see structure below).
2. CI workflow(s) to run tests on PRs and nightly schedules.
3. Test reports (HTML/JSON), code coverage, perf dashboards, and vulnerability reports.
4. Bug tickets (Jira/GitHub Issues) for all failures with reproduction steps, logs and suggested fixes.
5. Final QA report summarizing results, risk assessment, and remediation plan.

Recommended tools (suggested — you may substitute equivalents)
----------------------------------------------------------------
- Unit testing: Vitest (frontend) / Jest (backend) — use existing project conventions.
- Component / visual: Storybook + Chromatic or Playwright snapshots.
- E2E: Playwright (web).
- Integration / API: Postman collections + Newman, or Supertest + Vitest.
- Contract testing: Pact (consumer-driven contracts).
- Load / Stress / Scalability: k6 (scripts) and/or Artillery; optional wrk for micro-benchmarks.
- Performance: Lighthouse CI, WebPageTest (for key pages).
- Security SCA: Snyk / npm audit / GitHub Dependabot.
- Dynamic security testing (DAST): OWASP ZAP (CI integration).
- Penetration testing: manual + Burp Suite (in scope for security team), and automated OWASP ZAP active scans.
- Fuzzing: use simple HTTP fuzzers (fuzzing via k6 or boofuzz wrappers), or node-fuzz (fuzz inputs for API endpoints). For binary targets, suggest AFL / honggfuzz if applicable.
- Reliability & Chaos: Gremlin or a simpler chaos script that kills worker process / introduces DB latency in staging.
- Accessibility: axe-core (Pa11y or Playwright + axe).
- Docs testing: markdown link checker, validate OpenAPI/AsyncAPI schemas.
- Container/Infra checks: Trivy (image scanning).
- CI Reporter: Allure, JUnit XML outputs.

Repository test layout (create these folders)
--------------------------------------------
- `tests/unit/` — unit tests (vitest/jest)
- `tests/integration/` — integration tests (database + API)
- `tests/e2e/` — Playwright tests
- `tests/contracts/` — Pact contracts (consumer/provider)
- `tests/load/` — k6/Artillery scripts
- `tests/security/` — OWASP ZAP configs, Snyk scripts
- `tests/fuzz/` — fuzz scripts and harnesses
- `tests/perf/` — Lighthouse CI config & scripts
- `tests/utils/` — helpers for seeding, fixtures, mocks
- `docs/test-runbook.md` — step-by-step runbook for manual tests & environment setup

High level implementation tasks (do them in order)
--------------------------------------------------
A. Setup & baseline
  1. Create `tests/*` folders and add README for each folder describing purpose & how to run.
  2. Add or update `package.json` scripts:
     - `test:unit`, `test:integration`, `test:e2e`, `test:contract`, `test:load`, `test:security`, `test:fuzz`, `test:perf`, `test:ci` etc.
  3. Add test environment variables file `.env.test` with placeholders and docs for secrets needed.
  4. Wire up a test database and a mock/stub environment for external services (OpenAI/Spotify/Supabase) or use recorded fixtures.

B. Unit Testing (item 16)
  - Write unit tests for core functions, utilities, reducers, hooks, components logic.
  - Target coverage ≥ 80% for core modules (auth, signup, playlist worker, forum core).
  - Tools: Vitest + @testing-library/react for components, node test runner for server code.
  - Output: coverage report (lcov + html).

C. Contract Testing (item 17)
  - Implement consumer-driven contracts with Pact:
    - Consumers: frontend fetch layers / integration tests.
    - Providers: backend APIs.
  - Automate provider verification in CI.

D. Integration Testing (item 2)
  - Tests that exercise API endpoints end-to-end with DB (use test DB and rollback transactions or test containers).
  - Include: signup flow, artist verification queue, playlist create/publish, notifications, social promo generation.
  - Tools: Supertest + Vitest or Postman Newman collections.

E. End-to-End Testing (item 19)
  - Implement Playwright tests covering:
    - Sign up (user & artist) happy & negative flows.
    - Monthly playlist admin flow (validate, schedule, publish).
    - Social promo generate → preview → export (mock OpenAI where necessary).
    - Notifications & toast flows.
    - News filters & forum flows.
  - Add E2E CI job with Playwright test runner (headed/ headless with browsers).

F. Performance, Load & Stress Testing (items 3, 4, 12)
  - Create k6 scripts to simulate realistic traffic patterns:
    - Smoke load: 50 concurrent users hitting dashboard + playlist embed pages.
    - Peak load: 500–2000 virtual users depending on capacity.
    - Stress test: ramp to failure & observe system behaviors.
  - Metrics to capture: p95 latency, error rate, throughput, DB connections, CPU, memory.
  - Run tests in staging-like environment.
  - Configure thresholds and alerting: e.g., p95 < 2s, errorRate < 1%.
  - Artillery or k6 in CI nightly for regression.

G. Scalability Testing (item 13)
  - Evaluate horizontal scaling: scale app server instances / worker instances and re-run load tests to find linearity.
  - Validate DB connection pooling and ensure RLS policies not creating bottlenecks.

H. Reliability Testing (item 6)
  - Chaos/Resilience tests in staging:
    - Kill worker process mid-job, simulate DB latency, simulate external API outage (OpenAI/Spotify).
    - Ensure graceful retries and error states; no data corruption.
  - Tests to validate job resume, idempotency, and retry backoff.

I. Security Testing & Penetration (items 5 & 20)
  - Static Dependency Analysis:
    - Run `npm audit`, Snyk scan, Trivy image scans.
  - SAST (optional): run eslint-plugin-security and language-specific SAST if available.
  - DAST:
    - Run OWASP ZAP active scan against staging endpoints during off-hours; capture alerts in CI artifact.
  - Manual Penetration:
    - Run Burp Suite test cases for authentication flows, CSRF, XSS, IDOR, SQLi, SSRF attempt points (uploads, external URL parsers).
  - Secrets & config checks: ensure no secrets in repo, use environment/secret manager.
  - Produce remediation tickets with CVSS-style severity.

J. Fuzz Testing (item 10)
  - Implement fuzz harnesses for JSON REST endpoints:
    - Feed mutated payloads to signup, social promo generate, playlist create.
    - Look for crashes, 5xx responses, memory leaks.
  - Tooling: quick fuzz scripts using node-fuzz or k6 mutation scripts; log findings.

K. Compatibility Testing (item 14)
  - Test browsers: Chrome (latest), Firefox (latest), Safari (latest), Edge.
  - Test OS: macOS, Windows, Linux (desktop), iOS, Android (mobile).
  - Use Playwright capabilities or BrowserStack/SauceLabs for cross-browser/device matrix.

L. Usability Testing (item 7)
  - Prepare tasks and scripts for human testers:
    - Onboard as new artist and submit playlist.
    - Create social promo and export.
    - Moderate forum posts.
  - Capture task completion rates, time-on-task, and qualitative feedback.
  - Accessibility checks (axe-core) integrated into Playwright tests and Storybook.

M. Documentation Testing (item 8)
  - Validate all public docs and API docs:
    - Validate OpenAPI / Swagger definitions (if present).
    - Markdown link checker for docs.
    - Ensure migration/runbook docs up-to-date (docs/IMPLEMENTATION_NOTES.md, docs/MONTHLY_PLAYLISTS.md).
  - Verify README run commands work in a clean environment.

N. Regression Testing (item 9)
  - Run full test suite before merge; maintain a fast smoke suite for PRs.
  - Nightly full regression build that runs all suites and reports failures.

O. Error Handling Testing (item 15) & Negative Testing (item 18)
  - Create tests that trigger error branches:
    - DB down, S3 upload failure, invalid user tokens, malformed payloads.
  - Ensure API returns proper error codes, logged exceptions with context, and user-facing friendly messages.

P. Performance Testing (item 12)
  - Lighthouse for key pages (dashboard, signup modal, playlist page) with thresholds (e.g., performance > 80).
  - Measure TTFB, FCP, LCP, CLS; generate Lighthouse CI reports.

Q. Contract & Provider verification (item 17)
  - Run Pact verifier job in CI for provider. Fail on contract drift.

R. Penetration Testing (item 20)
  - Coordinate a manual pen-test (scope: staging only):
    - Test auth, privilege escalation, admin endpoints, file uploads, SQL/NoSQL injection, SSRF, unsafe deserialization.
  - Produce a remediation report with critical items fixed prior to prod release.

S. End-to-End & Smoke Test matrix (item 19)
  - Define a small fast smoke test suite to run on every PR: key user flows (login, signup, publish playlist, view playlist, generate promo).
  - E2E full tests run nightly.

T. Observability & Reporting
  - Integrate test result artifacts into CI (JUnit XML, Allure, Playwright HTML).
  - Produce centralized test report dashboard for stakeholders with pass/fail, flaky tests, coverage, perf stats, security vulnerabilities.
  - Add automatic test-failure templates that open issue with logs and reproduction steps.

U. Remediation & Triage
  - For each failing test, create issue with:
    - Steps to reproduce, logs, screenshots, stack traces, CI artifacts.
    - Priority (P0-P3) and owner assignment.
  - Re-run tests after fixes and mark as resolved.

Run & CI commands (examples)
----------------------------
- Install & setup:
  - `pnpm install`
  - `cp .env.example .env.test && fill secrets`
- Unit tests:
  - `pnpm test:unit` -> generates coverage at `coverage/index.html`
- Integration tests:
  - `pnpm test:integration`
- Playwright E2E:
  - `pnpm test:e2e`
- k6 load:
  - `k6 run tests/load/playlist-load.js`
- OWASP ZAP automated scan:
  - `zap-baseline.py -t https://staging.example.com -r zap_report.html`
- Pact provider verification:
  - `pnpm test:contract`
- Full CI run:
  - `pnpm run test:ci` (composed to run unit->contract->integration->e2e->security->perf)

Acceptance criteria (general)
----------------------------
- All unit tests pass and coverage > 80% for critical modules.
- No critical/high security vulnerabilities unresolved (Snyk/Trivy).
- E2E smoke suite passes on every PR.
- Load tests meet thresholds: p95 latency < SLA, error rate < 1%.
- No data corruption or job-loss observed in reliability tests.
- Manual pen-test finds no critical vulnerabilities; known issues have mitigations.
- Accessibility baseline met (axe violations = 0 major).
- All docs validated and runnable.

Reporting & artifacts
---------------------
- Upload these artifacts to the PR:
  - Unit coverage HTML/summary
  - Playwright HTML report
  - k6 load report (JSON + summary)
  - OWASP ZAP report (XML/HTML)
  - Snyk/vulnerability report
  - Pact verification report
  - Allure or JUnit XML test artifacts
  - Storybook snapshot links

Important constraints & notes
----------------------------
- Use mocked or sandbox accounts for external services (OpenAI, Spotify) to avoid costs/tokens leaking in CI.
- Run heavy load/stress/DAST tests in a dedicated staging environment only; coordinate with infra & on-call.
- Isolate destructive tests from production and sensitive data.
- Keep tests deterministic and avoid relying on flaky UI timings — use network stubbing where practical.
- Use fixtures and seed data for DB; teardown/clean after tests.
